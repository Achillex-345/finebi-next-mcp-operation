# 业务设计：看板按什么顺序回答问题

本 Skill 的规则分三层，越往上越稳定（D-043）：

| 层 | 回答什么 | 稳定性 | 放在哪 |
|---|---|---|---|
| 业务设计 | 看什么指标、凭什么判断好坏、往哪里拆、怎么解释原因 | 不随工具变 | 本文 |
| 建模设计 | 数据怎么组织，才能支持上面的判断 | 不随工具变 | `dashboard-architecture.md`、`modeling-method.md` |
| DSL 写法 | 在当前工具里具体怎么写 | 随工具和版本变 | 现查 MCP Help；Skill 只记谬误（`known-issues.md`、`chart-dsl.md`、lint） |

动手顺序也是这个顺序：先想清楚业务设计，再定建模，最后才写 DSL。

## 一、经营监控的推导链

下面这条链来自用户设计经营看板的思路，每一步都由上一步推出来：

1. **指标**：先定结果指标，以及它由哪些环节构成（指标链，如 量 × 转化 × 单值 = 结果）。
2. **判断逻辑**：数字本身没有好坏，要有参照。和目标比是达成率，和上一期比是环比，和去年比是同比。每个结果指标至少要有一种参照。
3. **时间切片**：有了同环比，就必须先定义“本期”。所以需要日期区间，对比期由本期推出来。
4. **维度切分**：同一个时间切片里，按组织层级、对象拆开，看谁好谁差、谁在拉动、谁在拖累。
5. **历史趋势**：某个切片下某个维度的数字可能“失真”。它没有算错，只是突发情况让这一段看起来特别好或特别差。所以要配一张不随切片变的长期趋势图，判断这是持续的走势还是一次性的波动。
6. **业务归因**：前五步都是结果视角，看的是达成得怎么样。再往下进入过程和构成视角（来源、品项等），解释结果为什么是这样。

第 6 步在逻辑上是更细的维度，本可以和第 4 步放在一起。单独成板块有两个理由：
- **业务上**：从“结果怎么样”切换到了“原因是什么”。
- **建模上**：这些维度放进主骨架会扇出，只能另建子表（`modeling-method.md` 七）。

## 二、怎么用

- **新需求先沿这条链提问**：结果指标是什么？好坏拿什么参照？时间切片怎么定？按哪些维度拆？要看多长的历史？哪些过程维度能解释结果？答不上来的地方向用户确认，不自己补。
- **它是思考顺序，不是模板**：有的业务没有目标，就只用同环比；有的业务没有过程数据，就到第 5 步为止。环节可以增减，但“结果 → 判断 → 切片 → 拆分 → 历史 → 归因”这个先后通常成立。
- **回溯已有看板时**，也按这条链解释“为什么这样设计”，再看建模是否撑得住每一步。

## 三、落到看板和建模

| 业务步骤 | 看板上是什么 | 建模层对应 |
|---|---|---|
| 指标 | 指标卡，按指标链从左到右 | 原子量入表、比率按链重算（modeling-method.md 五） |
| 判断逻辑 | 达成率、环比、同比，带好坏着色 | 目标摊到日（三）；三期对比（六） |
| 时间切片 | 日期区间控件 | 区间绑开始、结束参数（六） |
| 维度切分 | 组织交叉表下钻、对象排行 | 骨架带组织层级（二）；下钻表先汇总到最细对象（五） |
| 历史趋势 | 近 N 期趋势，不跟随切片 | 滚动窗口与同期取法（六） |
| 业务归因 | 过程或构成板块 | 子业务宽表、一致维度、跨表联动（七、八） |

- 看板区块的先后跟这条链走（modeling-method.md 八）；看板说明书里的分析步骤也沿这条链（九）。
- 计划态结构图（D-032）前先写一段业务设计：每一步对应哪个组件、为什么这样拆。用户确认的是业务设计和结构图两样东西。
